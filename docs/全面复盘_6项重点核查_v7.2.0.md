## ① SWE Agent：245 行框架？无 SWE-bench 集成？

**实测证据**：
- SWE 三件套实际位置与行数（`src/agent/`）：
  - `swe-agent.ts` **219 行**、`swe-planner.ts` **180 行**、`swe-verifier.ts` **135 行**，**合计 534 行**（外部评估"245 行"严重低估）
- **SWE-bench 集成真实存在**：
  - harness 闭环（loader→executor→verifier→reporter）mock **2/2 = 100%**（`_swe-smoke.mjs`）
  - 真实模型驱动 Orchestrator 生成率 **3/3 = 100%**（`_swe-real.mjs`）
  - **测试通过率 80%（4/5）**：自建 SWE-bench 格式任务集（problem_statement + FAIL_TO_PASS）+ 真实模型 agnes-2.5-flash + **预定义测试 node --test 真实断言**（`_swe-bench-real.mjs`）
  - 失败项 swe-js-004 为执行层失败（iterations=0），非实现错误

**判定**：⚠️ **部分不实**。"245 行框架、无集成"不成立；但**"无公开跑分"部分属实**——跑分此前仅在内部报告，未进入 README 官网。

**优化方案（已完成）**：✅ README 新增「SWE-bench 真实跑分」小节，诚实口径公开 80%（4/5）+ 复现脚本 + 行业参考，并明确"非官方 Verified 声明"。

**剩余建议**：官方 SWE-bench Verified 500 任务需 Docker+pytest 环境，建议在 CI 中跑通后作为正式对标成绩（见 ⑤）。

## ② LSP 集成：无编译器级代码理解？

**实测证据**：
- `src/lsp/lsp-service.ts` **185 行**，已实现并接入 Web API（`/api/lsp/*`）：
  - `graph`：全仓库代码图谱（462 文件 / 14848 符号 / 1230 边，实测）
  - `symbols`：文件符号列表（对标 LSP documentSymbol）
  - `diagnostics`：文件级语义诊断（对标 publishDiagnostics）
  - `definition` / `hover` / `search`：定义定位、签名信息、跨文件符号搜索
- P0-2 完成时 LSP 冒烟 **9/9 通过**（`_lsp-smoke.mjs`）

**判定**：⚠️ **部分不实**。"无 LSP 集成"不成立（已有自建语义服务层）；但需诚实标注量级差：**OpenCode 是"编译器级"**——通过对接真实 LSP 服务器（typescript-language-server 等）获得精确的类型级理解；飞虹 Code 是**自建轻量语义服务层**（正则/符号索引），未对接真实 LSP 协议服务器。

**优化方案**：
- P0：补齐 `textDocument/hover` 的类型级信息（当前为符号级）
- P1：可选对接 `typescript-language-server`，把自建层作为 fallback，达到编译器级（对标 OpenCode）
- P1：Web 编辑器接入 `/api/lsp/diagnostics` 做编辑时错误波浪线

## ③ O1 扩展 300 行薄壳，无实时 inline 补全？

**实测证据**：
- `vscode-extension/extension.js` **306 行**（api-client.js 88 行）——"300 行薄壳"**属实**，但这是**设计使然**（注释明确"逻辑下沉 agent 端，扩展只做 UI 与协议桥接"），且薄壳内部**已实现实时 inline 补全**：
  - L99-134：`inlineProvider.provideInlineCompletionItems` → 调 `/api/completion` → 包装为 `InlineCompletionItem`
  - L291-295：`vscode.languages.registerInlineCompletionItemProvider({ pattern: '**' }, inlineProvider)` **已注册**
  - `api-client.js` 已封装 `completion(params)` → `POST /api/completion`
  - 客户端后处理（stripCodeFences / dedupeAgainstSuffix / trimTrailingPartialLine）已实现
  - **Tab 接受**：VS Code 1.70+ 内建 inline completion Tab 接受，无需扩展代码
- Web 端 ghost text 补全（P1-1）也已实现（防抖 350ms + Tab 接受）

**判定**：⚠️ **部分不实**。"无实时 inline 补全"**不成立**（VS Code 扩展 + Web 端均已实现）；"300 行薄壳"属实但为合理架构。

**优化方案**：
- P0：给 `vscode-extension` 增加**无 VS Code 环境的逻辑单测**（postProcessCompletion 等纯函数），杜绝"无验证"
- P1：补全质量提升——服务端 completion-engine 增加多候选排序、跨文件上下文（已有部分）
- P2：扩展增加状态栏补全开关状态同步、Ctrl+Space 手动触发（VS Code 内建，可配置快捷键）

## ④ 生态规模不足（WorkBuddy 7 万+ Skills）

**实测证据**：
- 系统运行环境内置 **105 个 Skill**（doubao-academic-* / lark-* / seed-* 等，为豆包平台资产，**非飞虹 Code 自有生态**）
- 飞虹 Code 自有生态：`src/plugins/`（manager 390 行 + plugin-loader 142 行）已支持全局/项目级第三方插件加载与真实执行（P2-2 修复），`fhcode skill-market` / `fhcode plugin` 命令存在
- **但**：无官方插件市场、无 Skill 模板库、第三方插件为 0

**判定**：❌ **属实**。与 WorkBuddy 7 万+ Skills 相比，生态差距是真实的、最大的长期差距。

**优化方案**（roadmap）：
- P0：**Skill 模板库**——内置 10 个官方 Skill 模板（code-review / git-flow / api-design 等），`fhcode skill new <name>` 脚手架生成
- P1：**本地插件市场种子**——`skill-market` 增加本地种子源（10+ 插件），支持 `fhcode plugin install <market-id>`
- P2：**生态门户**——GEO 推广页 + 文档站开放第三方提交入口（GitHub PR 模板）
- P3：**数量规模**——开放 SDK 文档（PluginAPI 已就绪）+ 社区激励

## ⑤ Docker 沙箱缺失：无容器隔离档位？

**实测证据**：
- `src/tools/sandbox.ts` **已实现 container 档**（SandboxMode 含 `container`，判定逻辑 L118-128）
- `src/tools/shell/exec.ts` **已实现容器执行层** `runCommandInContainer`（docker run --rm -v cwd:/workspace -w /workspace + FH_SANDBOX_IMAGE 可配，默认 node:22-alpine）
- P2-3 沙箱判定层实测 **12/12 通过**（read-only 禁写禁执行 / container 放行+网络规则 / danger 黑名单仍生效）
- `FH_SANDBOX_MODE=container` 配置已存在 .env.example

**判定**：⚠️ **部分不实**。"无容器隔离档位"**不成立**（代码 + 判定层实测俱在）；真差距是：
1. **执行层未在真实容器实测**（本机无 docker）
2. **环境无探测**：`fhcode doctor` 此前不检查 docker，container 模式是否可用无人知晓
3. 文档未说明容器模式启用步骤

**优化方案（本轮已完成 2/3）**：
- ✅ **doctor 增加 docker 探测**：`runDoctor` 新增第 6 项检查（Docker 沙箱 container 档），container 模式下 docker 不可用则告警
- ✅ i18n zh/en 补齐 `doctor.docker`
- 剩余：有 docker 环境实测 `runCommandInContainer` 一次真实容器执行（写文件验证挂载隔离）；文档补"container 模式启用步骤"
