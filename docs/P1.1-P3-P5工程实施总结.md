## 二、P1.1 内核服务化改造

### 2.1 问题

Orchestrator 的装配逻辑散落在 `src/cli/run.ts` 的 `executeTask()` 中（约 130 行），Web 服务端、嵌入式场景无法复用。每次新增调用方都要重复装配 router / tools / eventLog / session / guard / persist / onEvent 等 15+ 个依赖。

### 2.2 方案

创建 `createAgentSession(config)` 工厂，封装全部装配细节，返回 `AgentSession` 对象：

```
createAgentSession(config)
  ├─ 自动创建：runId / eventLog / session / steerQueue / AbortController
  ├─ 调用方注入：router（必填）/ cwd（必填）
  ├─ 可选覆盖：tools / security / guard / approve / persist / onEvent / stageChange / ...
  └─ 返回 AgentSession { runId, steer, run(), injectSteer(), abort(), getSession(), getEventLog() }
```

### 2.3 关键设计决策

1. **router 必须由调用方提供**——支持离线 mock / 真实模型 / 自定义 provider，工厂不绑定任何模型配置
2. **tools 可选，默认 createDefaultRegistry()**——MCP / 企业守卫等高级组件由调用方注入
3. **内置 AbortController**——调用方不传 signal 时工厂内部创建，`abort()` 方法直接可用
4. **内置 steer 队列**——P3 的 InMemorySteerQueue 自动绑定到 OrchestratorDeps.steerSource
5. **不替代 executeTask**——CLI 仍可独立装配；工厂面向程序化 / Web 场景

### 2.4 新增文件

| 文件 | 行数 | 说明 |
|------|------|------|
| `src/agent/agent-session.ts` | ~170 | 工厂 + AgentSession 接口 + AgentSessionConfig |

### 2.5 使用示例

```typescript
import { createAgentSession } from './src/agent/agent-session';
import { ModelRouter } from './src/models/model-router';

const session = createAgentSession({
  cwd: '/path/to/project',
  router: new ModelRouter(providers, 'cost', 0),
  onEvent: (ev) => sseSend(ev),          // Web 流式推送
  stageChange: (path, content) => panel.add(path, content), // 变更面板
  security: { sandboxMode: 'workspace-write', requireApproval: true },
  maxIterations: 30,
});

// 运行中用户插话改方向（P3 steer）
session.injectSteer('不要改测试文件，只改 src/', '只改 src/ 目录');

// 执行任务
const result = await session.run('修复登录 bug');

// 中断
session.abort();
```

## 三、P3 steer() 中途人工纠偏

### 3.1 问题

任务运行中用户发现方向错误，需要插话改目标。原有机制只有 AbortSignal（完全中断）和 resume（停止后重启），缺少"不中断、不回滚、改方向继续"的能力。

### 3.2 方案

在 Orchestrator 主循环顶部（abort 检查之后、模型调用之前）增加 steer 事件源 drain：

```
for (每轮循环) {
  1. 检查 abort signal → 中断则退出
  2. ★ drain steer 队列 → 有消息则注入为 user 消息，重置错误/循环计数
  3. 模型调用（含重试）
  4. 无工具调用 → 完成
  5. 成本/迭代上限检查
  6. 原地打转检测
  7. 工具执行
  8. 错误自愈
  9. 上下文压缩
}
```

### 3.3 核心实现

**`src/agent/steer.ts`**——SteerSource 抽象 + InMemorySteerQueue：

```typescript
interface SteerSource {
  drain(): SteerMessage[];        // 取出所有待注入消息（消费后清空）
  push(msg): SteerMessage;         // 推入一条消息（线程安全）
  size(): number;                  // 待消费消息数
}
```

**`src/agent/orchestrator.ts`**——主循环注入（约 25 行）：

```typescript
if (this.deps.steerSource) {
  const steers = this.deps.steerSource.drain();
  for (const s of steers) {
    const steerMsg: ChatMessage = {
      role: 'user',
      content: `[用户中途指令] ${s.message}${s.focus ? `\n\n聚焦：${s.focus}` : ''}\n\n请基于当前已完成的工作，按此新指令继续执行。已确认的文件变更保留，不要回滚。`,
    };
    messages.push(steerMsg);
    session.append(steerMsg);
    await eventLog.append('steer', { steerId: s.id, message: s.message.slice(0, 500), iteration: calls });
    this.deps.onEvent?.({ type: 'steer', steerId: s.id, message: s.message, iteration: calls });
    consecutiveErrors = 0;   // 重置错误计数
    sameTextStreak = 0;      // 重置循环检测
    lastAssistantText = '';
  }
}
```

### 3.4 关键设计决策

1. **steer ≠ abort**——steer 是"改方向"，abort 是"停止"；两者独立，steer 不触发中断
2. **不回滚已确认变更**——steer 消息明确告知模型"已确认的文件变更保留"，change-manager 暂存状态不动
3. **重置错误/循环计数**——新方向不应继承旧方向的错误累积，避免自愈机制误判
4. **事件可审计**——新增 `steer` 事件类型到 EventLog 和 OrchestratorEvent，企业审计可追溯
5. **SteerSource 抽象**——默认 InMemorySteerQueue；Web/SSE 场景可自定义（如 Redis Stream、消息队列）
6. **注入时机**——循环顶部 drain，确保模型在下一轮请求中看到新指令；不在工具执行中途注入（避免状态不一致）

### 3.5 与 Pi steer() 对照

| 维度 | 飞虹Code steer | Pi steer |
|------|---------------|----------|
| 注入方式 | SteerSource.drain() 在循环顶部消费 | agent.steer() 队列，当前 assistant turn 结束后注入 |
| 消息格式 | 包装为 `[用户中途指令]` user 消息 | 原始 AgentMessage 直接入队 |
| 状态重置 | 重置 consecutiveErrors / sameTextStreak | 由 Agent 内部状态机管理 |
| 审计 | eventLog.append('steer') + onEvent | telemetry span 事件 |
| 分布式 | SteerSource 可替换为 Redis 实现 | 单进程队列 |

### 3.6 新增 / 修改文件

| 文件 | 操作 | 说明 |
|------|------|------|
| `src/agent/steer.ts` | 新增 | SteerSource 接口 + InMemorySteerQueue + createSteerQueue |
| `src/agent/orchestrator.ts` | 修改 | OrchestratorDeps 加 steerSource；OrchestratorEvent 加 steer；主循环注入逻辑 |

### 4.4 关键发现

1. **两端均能完成 ReAct 闭环**：模型→工具→结果→总结，Mock 模式下全部成功
2. **steer() 两端均生效**：
   - 飞虹Code：steer 在 orchestrator 循环顶部 drain，模型下一轮请求中可见 `[用户中途指令]` 标记
   - Pi：`agent.steer()` 队列注入，当前 assistant turn 结束后生效
3. **飞虹Code 企业级能力完整**：RBAC / SHA-256 哈希链审计 / 4 模式沙箱 / diff 草稿变更管理 / 逐 hunk 确认——Pi 内核不含这些，需自行封装
4. **Pi 内核抽象更干净**：Agent 类原生支持 steer / followUp 队列、QueueMode（all / one-at-a-time）、ToolExecutionMode（sequential / parallel）、telemetry schema——飞虹Code 需自研这些抽象
5. **Pi 是 ESM-only**：`"type": "module"`，要求 Node >= 22.19.0；飞虹Code 是 CJS，混用时需 `.mts` + tsx

使用 agnes-ai.cn API（agnes-2.5-flash）跑真实模型对照评测，3 个任务两端全部通过：

| 任务 | 飞虹Code 迭代 | Pi 迭代 | 飞虹Code 工具 | Pi 工具 | 飞虹Code 耗时 | Pi 耗时 | 飞虹Code 成功 | Pi 成功 |

**总体**：飞虹Code 3/3 成功，平均 1.3 轮迭代；Pi 3/3 成功，平均 2.3 轮迭代。

**关键发现**：
1. 两端 steer() 在真实模型下均生效——用户中途插话"不要创建 test.txt，改成创建 result.md"后，两端均按新指令创建了 result.md 而非 test.txt
