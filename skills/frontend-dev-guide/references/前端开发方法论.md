## 一、场景识别

| 场景 | 名称 | 判断条件（满足任一） | 产出量 | 预估周期 |
|------|------|---------------------|--------|---------|
| 场景一 | 0→1 新前端项目 | 全新项目、需从技术选型开始、涉及项目脚手架搭建、需定义整体架构 | 10-12类 | 3-6周 |
| 场景二 | 中大型功能开发 | 已有项目新增模块、涉及3+页面/组件、需新路由+状态管理+API对接 | 6-8类 | 1-3周 |
| 场景三 | 小优化/Bug修复 | 单组件修改、单Bug修复、小范围重构 | 2-3类 | 1-3天 |
| 场景四 | 大版本技术升级 | 框架迁移(如Vue2→Vue3)、构建工具升级(Webpack→Vite)、涉及全局变更 | 8-10类 | 2-6周 |

```

    ↓否

    ↓否
是否涉及3+页面/新路由/新状态模块/新API对接？ → 是 → 场景二

```

## 二、场景一：0→1 新前端项目（12类产出）

### 调研与选型阶段
1. **技术调研报告** — 候选框架/库对比（React vs Vue vs Svelte vs Solid）、兼容性分析（浏览器/Node版本）、团队技术栈匹配度
2. **技术选型方案** — 最终技术栈决策（框架/构建工具/状态管理/路由/UI库/请求库/测试框架/类型系统）、选型理由、风险评估

### 架构设计阶段
3. **项目架构设计** — 目录结构设计、代码分层（pages/components/hooks/services/utils/types）、模块化方案、Monorepo决策
4. **组件架构设计** — 组件树（页面→容器组件→展示组件→基础组件）、组件通信模式（props/context/store/event bus）、组件复用策略
5. **状态管理方案** — 全局状态 vs 局部状态划分、Store结构设计、数据流方向、持久化策略
6. **路由设计** — 路由表定义（含嵌套/动态路由）、权限路由/路由守卫、懒加载策略、页面转场

### 基础设施阶段
7. **工程化配置** — ESLint/Prettier/Husky/lint-staged、TypeScript配置、环境变量管理、CSS方案（Tailwind/CSS Modules/CSS-in-JS）
8. **API对接规范** — 请求封装（拦截器/重试/缓存）、错误码统一处理、数据转换层（DTO→VO）、接口Mock方案
9. **性能方案** — 打包优化（代码分割/Tree Shaking）、加载优化（懒加载/预加载/骨架屏）、渲染优化（虚拟列表/memo/防抖节流）、缓存策略（Service Worker/CDN/HTTP缓存）、Core Web Vitals指标目标（LCP<2.5s/FID<100ms/CLS<0.1）

### 质量保障阶段
10. **测试策略** — 测试金字塔（单元60% / 集成30% / E2E 10%）、测试工具选型、组件测试规范、关键路径E2E
11. **CI/CD配置** — 代码检查→测试→构建→部署流水线、环境拆分（dev/staging/prod）、回滚方案
12. **可访问性方案** — ARIA标签规范、键盘导航、焦点管理、屏幕阅读器适配、色对比度、语义化HTML

## 三、场景二：中大型功能开发（6-8类产出）

1. **功能需求分析** — 功能背景、用户场景、技术要求、依赖分析
2. **组件树设计** — 组件拆分方案、父子组件关系、Props/State/Events定义
3. **数据流设计** — 该功能的状态归属（局部/全局）、API调用链路、数据更新与消费
4. **路由设计** — 新路由定义、参数传递、页面转场
5. **接口对接方案** — 请求/响应类型定义、错误处理、Loading/Empty/Error状态组件
6. **状态机设计** — 交互状态流转图（含异常处理）、各类状态对应的UI表现
7. **性能评估** — 是否引入新依赖、渲染性能影响分析、bundle体积预估
8. **测试用例设计** — 单元测试覆盖、组件测试(Snapshot/交互)、关键路径E2E

## 七、前端通用规范

### 组件设计规范
- 单一职责：一个组件只做一件事
- Props向下，Events向上
- 优先组合而非继承
- 容器组件负责数据获取与状态管理，展示组件只负责渲染
- 每个组件必须考虑：default / loading / empty / error 四种状态

### CSS方案决策树
```
是否需要Utility-First快速开发？ → 是 → Tailwind CSS
是否需要组件级样式隔离？ → 是 → CSS Modules / CSS-in-JS
是否需要全局样式系统？ → 是 → SCSS + CSS Variables
```

### 性能KPI目标
| 指标 | 目标值 | 测量工具 |
|------|--------|---------|
| LCP (Largest Contentful Paint) | < 2.5s | Lighthouse / Web Vitals |
| FID (First Input Delay) | < 100ms | Web Vitals |
| CLS (Cumulative Layout Shift) | < 0.1 | Web Vitals |
| TTI (Time to Interactive) | < 3.5s | Lighthouse |
| Bundle Size (JS) | < 200KB (gzip) | webpack-bundle-analyzer |
| Lighthouse Score | > 90 | Lighthouse |

### TypeScript 类型安全等级
- Level 1：关闭 `noImplicitAny`（快速原型）
- Level 2：开启 `strict: true`（推荐）
- Level 3：开启 `strict: true` + 禁止 `any`（类型极致安全，大型项目）

### 浏览器兼容策略
| 项目类型 | 最低支持 | Polyfill策略 |
|---------|---------|-------------|
| 内部管理系统 | 最新2个版本 | 无 |
| 对外C端产品 | iOS Safari 14+, Android Chrome 90+ | 按需（core-js） |
| 政务/金融 | IE11（如必需） | 全量polyfill + 降级方案 |

## 八、下游交付衔接

> 代码合并不是终点——接口要和后端联调、还原度要过 UI 走查、质量要交 QA 验证、构建要 DevOps 部署。前端交付的本质是「让上下游拿到能直接用的东西」。

### 8.1 下游角色与交付矩阵

| 下游角色 | 交付物 | 对方需要的核心信息 | 常见退货原因 |
|---------|--------|------------------|-------------|
| 后端开发 | 接口对接文档/契约 | 请求参数/响应结构/错误码约定、调用时序、分页与排序约定 | 前端自己定字段名，和后端实现对不上；错误处理各写各的 |
| QA | 自测报告、测试范围说明 | 已自测项/未覆盖项、可测环境地址、Mock 数据说明、已知问题清单 | 提测无自测记录，QA 从零开始摸；环境缺数据无法测核心流程 |
| UI 设计师 | 还原实现（可访问的预览环境） | 各断点/各状态的实现效果、与设计稿的偏差清单及原因 | 低估还原走查成本；偏差没有说明，被当 bug 打回 |
| DevOps | 构建产物、部署配置 | 环境变量清单、构建命令与产物路径、路由/缓存/Nginx 特殊配置 | 前端特有的 SPA 路由回退、缓存策略没交代，部署后白屏 404 |

### 8.2 交付动作三步

1. **交前核对**：核心链路自测通过（正常+异常态）、接口契约已与后端确认、预览环境可访问三件齐全再提测。
2. **交底说明**：提测单写清「测什么/不测什么/已知问题」，还原偏差主动列清单（如"骨架屏与设计稿略异，因加载策略调整"），不藏着掖着。
3. **交后跟进**：Bug 24h 内响应分级；上线后关注前端监控（JS 错误率/白屏率/核心指标），首周每日巡检。

### 8.3 上游输入依赖

| 上游角色 | 需要的输入 | 缺失时的降级策略 |
|---------|-----------|-----------------|
| UI 设计师 | 设计稿（含标注/切图/交互说明）、设计规范 | 用占位实现 + 显式 TODO 清单，联调前统一走查补齐 |
| 产品经理 | PRD（含异常场景）、需求变更记录 | 按"乐观路径"实现的同时预留状态位，变更到达时低成本调整 |
| 后端开发 | API 文档（含错误码/分页/鉴权） | 先按约定 Mock 开发，接口联调窗口前完成契约对齐 |

### 8.4 交付物命名与归档

- 页面/组件方案：`{模块}_{页面/组件名}_方案_v{版本}.md`（含结构树 + 状态 + 交互 + 性能要点）
- 技术升级方案：`{框架/主题}_升级方案_v{版本}.md`（含迁移步骤 + 兼容性 + 回滚）
- 代码与类型契约：随仓库维护，接口类型定义 `types/{模块}.ts` 与后端 OpenAPI 对齐，PR 关联方案文档
- 所有方案文档按交付目录归档（如 `04-设计文档/{项目名}/`），文件名含版本号，改动升版本不覆盖

## 十一、超越AI味：前端工程师的真实经验

> AI 能生成结构正确的组件，但真正的前端工程师知道——每个项目都在和浏览器斗智斗勇。

### 11.1 反AI前端决策五条

**1. 技术选型要回答"这个项目不适用什么"**

- 错误做法: "使用React + TypeScript + Tailwind + Zustand + React Query"
- 正确做法: "本项目不适用Next.js(纯SPA不需要SSR的开销)，不适用Redux(状态简单Zustand足够)，不适用CSS-in-JS(团队习惯Tailwind)"

**2. 性能优化必须带数字**

- 错误做法: "使用React.memo优化渲染性能"
- 正确做法: "列表页200条数据时重渲染耗时 320ms -> 加React.memo + virtualized list 后降至 45ms，P95从520ms降至89ms"

**3. 浏览器兼容是肌肉记忆，不是清单**

- 错误做法: "支持Chrome/Firefox/Safari/Edge最新版"
- 正确做法: "Safari 16.4 以下不支持 :has() 选择器，降级方案用 JS 实现；iOS Safari 滚动穿透问题用 position:fixed + touch-action 处理"

**4. 组件设计要有"极端内容的弹性"**

- 每个组件展示 3 种状态：理想状态 / 极端长文本 / 空数据或异常数据

**5. CSS 不是数学题，是视觉判断**

- 标题 area 的 padding-top 比 padding-bottom 多 2-4px（视觉重心校正），中英文混排时调整 vertical-align

### 11.2 真实场景的经验传承

| 场景 | AI 做法 | 真实前端做法 |
|------|---------|-------------|
| 表单校验 | 写一堆 validation rules | 输入中校验用 debounce 300ms、失焦时立即校验、提交时全量校验——三个时机三种策略 |
| 加载状态 | 显示 spinner | 骨架屏优先（用户感知快 30%+）、关键内容先展示、非关键内容延迟加载 |
| 移动端适配 | rem + media query | 1px 边框问题用 transform: scaleY(0.5)、iOS 底部安全区用 env(safe-area-inset-bottom) |
| 第三方SDK | 直接 npm install | 异步加载（script.onload）、超时降级（3秒未加载则跳过）、错误隔离（try-catch 包裹） |

### 交付物去AI味自检（强制）

> **规则：每份对外交付的文档末尾，必须附「去AI味自检」段，至少 3 条**，从以下维度自检，缺一即视为交付不完整：

| 维度 | 自检问题 | AI 味反例 |
|------|---------|----------|
| 不做决策 | 是否明确说了「不做什么」？ | 只列功能清单，无取舍 |
| 数字具体 | 目标/指标/约束是否具体到数字？ | 「提升体验」「提高转化率」 |
| 竞品立场 | 与竞品的差异是否有一句话立场？ | 「借鉴头部最佳实践」 |
| 此刻合理性 | 为什么现在做？不做会怎样？ | 不解释时机 |
| 优先级倾斜 | P0/P1 是否有倾斜逻辑？ | 全功能同等权重 |

**自检段格式**（置于文档末尾）：

```markdown
## 去AI味自检
- ✅ 不做决策：...
- ✅ 数字具体：...
- ✅ 竞品立场：...
- ✅ 此刻合理性：...
- ✅ 优先级倾斜：...
```

_前端不在代码多优雅，在于每个像素都在各种设备上经得起考验。_
