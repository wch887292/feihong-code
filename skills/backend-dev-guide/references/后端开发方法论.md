## 二、场景一：0→1 新后端服务（12类产出）

### 调研与选型
1. **技术调研报告** — 候选方案对比（语言/框架/DB/缓存/MQ/网关）、团队匹配度、社区活跃度
2. **技术选型方案** — 最终技术栈决策、选型理由与权衡、风险评估

### 架构设计
3. **系统架构设计** — 架构图(C4模型：Context→Container→Component)、部署拓扑、服务通信方式(HTTP/gRPC/MQ)、分层设计(Controller→Service→Repository→Domain)
4. **API设计** — 接口规范(RESTful/GraphQL/gRPC)、请求/响应格式、错误码体系、版本策略(URL/v{version}或Header)、分页/排序/筛选规范
5. **数据库Schema设计** — ER图、表结构定义（字段/类型/约束/默认值）、索引策略（主键/唯一/普通/联合/覆盖索引原则）、分库分表策略、读写分离方案
6. **数据流设计** — 核心业务流程数据流、异步任务处理（消息队列/事件驱动）、数据一致性策略

### 基础设施
7. **缓存策略** — 多级缓存架构（本地→Redis→DB）、缓存穿透/击穿/雪崩防护方案、缓存更新策略（Cache Aside/Write Through/Write Behind）、TTL设计
8. **消息队列设计** — Topic/Queue规划、消息格式定义、消费者设计、死信队列、消息幂等、顺序消费方案
9. **安全方案** — 认证(JWT/OAuth2/Session)、授权(RBAC/ABAC)、接口安全(参数校验/防注入/防重放/限流)、数据安全(加密存储/脱敏/审计日志)、CORS/CSRF/XSS防护

### 质量保障
10. **日志与监控方案** — 日志规范（级别/格式/链路追踪ID）、APM工具选型、核心指标（QPS/延迟/错误率/资源利用率）、告警规则（阈值/分级/通知方式）
11. **灾难恢复方案** — RPO/RTO目标、备份策略（全量/增量/异地）、故障转移（主备/多活）、数据恢复演练计划
12. **CI/CD配置** — 构建→测试→部署流水线、环境管理（dev/staging/prod）、数据库Migration管理、回滚方案

## 三、场景二：中大型功能/模块开发（6-8类产出）

1. **功能需求分析** — 功能背景、业务场景、上下游依赖
2. **模块架构设计** — 模块在系统中的位置、内部组件划分、与现有模块的交互
3. **API接口定义** — OpenAPI/Swagger规范、请求/响应Schema、错误码、速率限制
4. **数据模型设计** — DDL语句、索引设计、数据迁移（Migration脚本）
5. **业务逻辑流程设计** — 核心流程时序图/活动图（含异常分支+补偿逻辑）、状态机设计（订单/审批等有状态实体）
6. **性能评估** — SQL执行计划分析、慢查询预估、缓存命中率预估、是否需要异步处理
7. **测试方案** — 单元测试(核心逻辑)、集成测试(API)、压力测试(关键接口QPS目标)
8. **影响面评估** — 上下游服务影响、数据库表变更影响、API兼容性分析

## 五、场景四：大版本重构/架构升级（8-10类产出）

1. **架构升级评估报告** — 升级动机、现有架构痛点量化分析、预期收益、工作量评估
2. **新架构设计方案** — 目标架构图、技术栈选择、与旧架构对比

4. **服务拆分/合并方案** — DDD限界上下文分析、微服务拆分原则（单一职责/高内聚低耦合）、数据拆分（分库/独立Schema）
5. **灰度切换方案** — 流量切换策略（百分比/用户/租户）、Canary Release、新旧服务并行运行
6. **API兼容性方案** — Breaking Change清单、废弃接口过渡期、客户端迁移指南
7. **性能容量评估** — 新旧架构QPS对比、资源需求评估、扩容方案
8. **监控告警升级** — 新增监控指标、告警规则更新、新旧架构对比Dashboard
9. **测试策略** — 对比测试（新旧架构输出一致性）、性能回归测试、混沌工程测试
10. **回滚预案** — 触发条件、回滚步骤、数据回滚验证、通知机制

## 七、后端通用规范

### API设计规范
- 资源命名：名词复数（`GET /api/v1/users`）
- HTTP方法语义：GET查询/POST创建/PUT全量更新/PATCH部分更新/DELETE删除
- 统一响应格式：
```json
{
  "code": 0,
  "message": "success",
  "data": {},
  "request_id": "uuid"
}
```
- 错误码规范：4位数模块码 + 3位数具体错误（如 1001001 = 用户模块+参数错误）
- 分页规范：`page`/`page_size`（默认20，最大100）

### 数据库设计规范
- 表名：复数/下划线（`users`, `order_items`）
- 必备字段：`id`(主键)、`created_at`、`updated_at`
- 软删除：`deleted_at` + 唯一索引包含此字段
- 避免：外键约束（应用层保证）、JSON字段存业务数据
- 索引原则：WHERE/JOIN/ORDER BY字段建索引、联合索引最左前缀、避免过多索引

### 分布式系统设计原则
- **CAP权衡：** 优先CP（一致性+分区容错）还是AP（可用性+分区容错），需明确决策
- **幂等性：** 关键写操作必须支持幂等（唯一键/Token/状态机）
- **分布式事务：** 优先避免→最终一致性→Saga/TCC→2PC（极不得已）
- **限流熔断：** 令牌桶/滑动窗口限流、熔断器（Closed→Open→Half-Open）
- **降级策略：** 核心链路降级预案、非核心功能可降级/关闭

### 安全清单
| 类别 | 要求 |
|------|------|
| 认证 | 密码哈希(Argon2/bcrypt)、JWT短期+Refresh Token |
| 授权 | 最小权限原则、API级别权限控制 |
| 输入 | 参数校验白名单、SQL注入防护(参数化查询)、XSS过滤 |
| 传输 | HTTPS强制、敏感数据加密传输 |
| 存储 | 密码不可逆加密、敏感字段AES加密、日志脱敏 |
| 运维 | 最小端口暴露、非root运行、定期依赖扫描 |

### 性能KPI
| 指标 | 目标值 |
|------|--------|
| API P95延迟 | < 200ms（内部）/ < 500ms（外部） |
| API P99延迟 | < 500ms（内部）/ < 1s（外部） |
| 数据库慢查询 | 单次 < 100ms，占比 < 1% |
| 缓存命中率 | > 90% |
| 系统可用性 | 99.9%（3个9）→ 月故障<43min / 99.99%（4个9）→ <4.3min |

## 八、下游交付衔接

> 后端方案不是接口文档写完就结束——API 要前端联调、要 QA 测试、要 DevOps 部署。明确「给谁用、对方要什么」，后端产出才能被高效消费。

### 8.1 下游角色与交付矩阵

| 下游角色 | 交付物 | 对方需要的核心信息 | 常见退货原因 |
|---------|--------|------------------|-------------|
| 前端开发 | API 接口文档、Mock 数据、联调环境 | 请求/响应 Schema、错误码含义、鉴权方式、分页/排序约定、字段空值语义 | 只有字段名没有字段含义；错误码不区分可重试/不可重试；文档与实现不一致 |
| QA | 接口测试点、测试环境、造数脚本 | 核心接口边界值、异常分支、性能指标（QPS/延迟）、数据准备方法 | 只给接口不给测试数据；异常场景没定义清楚 |
| DevOps | 部署配置、依赖清单、健康检查接口 | 环境变量清单、依赖服务与版本、启动顺序、健康检查端点、日志格式 | 硬编码配置散落；依赖版本没锁定；没有健康检查接口 |
| 技术负责人 | 架构设计文档、技术选型说明、风险评估 | 架构决策与理由、容量预估、单点风险、技术债清单 | 只有结论没有决策依据；风险没量化 |

### 8.2 交付动作三步

1. **交前核对**：接口文档已与实现对齐（Swagger 生成与手写一致）、Mock 数据可跑通前端主流程、错误码语义完整（可重试/不可重试/客户端错误/服务端错误）三件齐全再交。
2. **交底说明**：面向前端重点讲「字段语义与异常分支」——哪些字段可能为空、哪些错误码需要前端重试；面向 DevOps 讲「依赖与启动顺序」——环境变量、服务依赖、健康检查。
3. **交后跟进**：联调期间驻场响应接口问题，上线后观察一周接口错误率，性能不达标接口及时优化。

### 8.3 上游输入依赖

| 上游角色 | 需要的输入 | 缺失时的降级策略 |
|---------|-----------|-----------------|
| 产品经理 | PRD、业务流程图、数据规则 | 按最小可用起步（核心接口先行），显式声明假设并要求评审前补齐 |
| 技术负责人 | 架构方案、技术选型约束、SLA 目标 | 按团队既有技术栈默认选型，标注待确认项 |

### 8.4 交付物命名与归档

- 接口文档：`{服务名}_API_v{版本}.yaml`（OpenAPI 格式），与 Swagger 在线地址互链
- 数据库设计：`{库名}_DB设计_v{版本}.md`（含 DDL + ER 说明 + 索引设计）

## 十一、超越AI味：后端工程师的真实经验

> AI 能画出完美的架构图，但真正的后端工程师知道——架构的价值不在优雅，在于上线后不出事。

### 11.1 反AI后端决策五条

**1. 架构设计要从"为什么不需要"开始思考**

- 错误做法: "微服务 + 消息队列 + Redis + ES + K8s"（标准套餐）
- 正确做法: "日活不到 10 万，单体架构 + 模块化设计够用。不需要微服务（运维成本>收益），不需要消息队列（异步场景用数据库轮询即可）"

**2. API 设计要有"被攻击"的意识**

- 错误做法: GET /api/users -> 返回所有用户
- 正确做法: GET /api/users -> 默认分页 + 最大 pageSize=100 + 敏感字段脱敏 + 频率限制 100/min/ip

**3. 数据库设计要有"反三范式"的勇气**

- "订单快照表把商品名/价格/图片冗余存储——即使商品表后续修改，历史订单数据不变。这是故意的反范式"

**4. 缓存不是万能药**

- 缓存穿透：布隆过滤器。缓存击穿：互斥锁。缓存雪崩：过期时间加随机值。缓存和DB一致性：先更新DB再删缓存，失败用MQ重试

**5. 日志和监控要能回答"现在出什么事了"**

- 每个 API 最少 3 条日志：请求入口（method+path+userID）、关键业务节点（订单状态变更from->to）、异常（stackTrace+requestID）。告警不是'CPU>80%'——是'支付接口P95>3s 持续5分钟'

### 11.2 后端直觉检查清单

| 如果... | 那就... | 否则就是 AI 方案 |
|---------|---------|-----------------|
| 没有回滚方案 | 不要上线 | AI 方案总假设一切顺利 |
| SQL 没写 LIMIT | 加上 LIMIT | AI 从不担心全表扫描 |
| 接口没有幂等性 | 加上幂等键 | AI 假设网络永远可靠 |
| 没有讨论 CAP | 明确 CP 还是 AP | AI 不知道分布式系统有取舍 |
