# qwen3:8b 优化提升方案

> 分析日期：2026-10-01 ｜ 目标模型：qwen3:8b（通义千问第 3 代，8.19B 参数）
> 运行环境：Intel Core i5-12400 / 32GB RAM / Intel UHD 730 核显（已被 Ollama dropping）/ CPU 推理
> 当前基线：Ollama 0.33.1，Q4_K_M 量化（4.86 GiB），n_ctx=4096，6 线程，约 5 tokens/s

---

## 环境现状速览

从 Ollama 日志中可以直接读出以下关键事实：

- 模态文件类型：**Q4_K_M**（file_type=15），文件大小 4.86 GiB，5.10 BPW
- 模型架构：qwen3，36 层，hidden=4096，FFN=12288，32 注意力头 + 8 KV 头（GQA=4），RoPE base=1e6，vocab=151936，训练上下文 40960
- GPU 状况：Intel UHD Graphics 730 被 Ollama dropping（`OLLAMA_IGPU_ENABLE=1` 可尝试启用核显，但 UHD 730 的 Vulkan compute=0.0，基本不可用），当前纯 CPU 推理
- 系统内存：32 GiB 总量，可用约 13 GiB，swap 40 GiB
- 当前推理速度：约 **4.8~5.2 tokens/s**（CPU，6 线程，batch=512，上下文 4096）
- KV cache：576 MiB（4096 tokens × 36 层 × f16 K+V）
- 服务端配置：n_parallel=1，keep_alive=5m，num_ctx 默认 4096，thinking=0（未开启）
- prompt cache 已启用（上限 8192 MiB），context checkpoints 已启用

**核心矛盾**：模型 Q4_K_M 体积适中（4.86 GiB），但 CPU 推理速度只有约 5 tokens/s，首 token 延迟高（prompt eval 62s/2050 tokens），且 thinking 模式未开启。优化重点应该放在 **提升吞吐、降低首 token 延迟、开启 thinking 模式、以及通过提示词工程提升实际可用性**。

## 1. 量化压缩

### 1.1 现状

当前 Ollama 拉取的 qwen3:8b 已经是 **Q4_K_M** 量化版本（4.86 GiB，5.10 BPW）。这是 llama.cpp 的 K-quant 系列中「质量/体积」平衡最好的一档，对于 8B 模型来说，Q4_K_M 通常是**甜点档位**。

### 1.2 各量化档位对比（针对 qwen3:8b，基于 8.19B 参数、36 层、4096 hidden）

| 档位 | 预期体积 | 内存占用（加载） | 推理速度提升 | 精度损失（相对 FP16） | 适用场景 |
|------|---------|----------------|------------|-------------------|---------|
| **FP16（原始）** | ~16.4 GB | ~16.4 GB | 基准 | 无 | 有 GPU 时 |
| **Q8_0** | ~8.2 GB | ~8.2 GB | ~1.0×（接近无损） | <0.5%（几乎无感） | 追求极致质量、内存充足 |
| **Q6_K** | ~6.1 GB | ~6.1 GB | ~1.05× | 1~2%（极轻微） | 高质量 + 较小体积 |
| **Q5_K_M** ⭐ | ~5.4 GB | ~5.4 GB | ~1.15× | 2~4%（可接受） | **推荐甜点** |
| **Q4_K_M** ✅ 当前 | ~4.9 GB | ~4.9 GB | ~1.3× | 4~7%（轻微可感知） | **当前已用，性价比好** |
| **Q4_K_S** | ~4.3 GB | ~4.3 GB | ~1.4× | 5~8% | 内存紧张时 |
| **IQ4_XS** | ~4.0 GB | ~4.0 GB | ~1.35× | 6~10% | 极端体积敏感 |
| **Q3_K_M** | ~3.5 GB | ~3.5 GB | ~1.6× | 8~12% | 低端机/移动端 |
| **Q2_K** | ~2.9 GB | ~2.9 GB | ~1.8× | 15~20% | 极限压缩，质量下降明显 |

> **说明**：以上体积为近似值，实际以 llama.cpp `quantize` 输出为准。速度提升是相对 FP16 在同一硬件上的理论值；实际 CPU 推理中，量化主要减少内存带宽压力，对吞吐的提升在 10~30% 之间，对首 token 延迟的改善有限（首 token 主要受 prompt eval 量影响）。

### 1.3 推荐量化档位

**对于本机（32GB 内存、纯 CPU 推理）**：

- **保持 Q4_K_M 即可**。当前 4.86 GiB 的体积已经可以在 13GB 可用内存下流畅运行，再往下压缩到 Q3_K_M 会带来 8~12% 的精度损失，收益不成比例。
- 如果希望**极致速度**且能接受轻微质量下降：用 **Q5_K_M**（约 5.4 GB），推理速度可提升约 10~15%，精度损失仅 2~4%，在编程任务中几乎无感。
- 如果希望**最小体积**（比如拷贝到其他机器）：**Q4_K_S**（约 4.3 GB）或 **IQ4_XS**（约 4.0 GB）。
- **不推荐 Q8_0**：体积翻倍到 8.2 GB，但速度几乎不提升（CPU 下瓶颈在内存带宽而非计算），性价比低。

### 1.4 落地命令

#### 方案 A：用 llama.cpp 重新量化（如果你有 FP16 原始权重）

```bash
# 前置条件：已编译 llama.cpp（含 quantize 工具）
# 如果没有，用 git clone 后 cmake build，或直接用 ollama 自带的 llama-server 同目录下的工具

# 1. 如果你有 FP16 的 safetensors 原始权重（HuggingFace 格式）
#    先用 llama.cpp 的 convert 工具转为 GGUF：
python llama.cpp/convert_hf_to_gguf.py \
  --model-dir /path/to/Qwen3-8B \
  --output-dir /path/to/output \
  --outtype f16

# 2. 从 FP16 GGUF 量化到 Q5_K_M（推荐）：
./llama.cpp/build/bin/llama-quantize \
  /path/to/output/qwen3-8b-f16.gguf \
  /path/to/output/qwen3-8b-q5_k_m.gguf \
  Q5_K_M

# 3. 或者量化到 Q4_K_S（更小体积）：
./llama.cpp/build/bin/llama-quantize \
  /path/to/output/qwen3-8b-f16.gguf \
  /path/to/output/qwen3-8b-q4_k_s.gguf \
  Q4_K_S
```

#### 方案 B：用 Ollama 指向已有的 GGUF（无需重新量化）

如果你已经有一个量化好的 GGUF 文件（比如从 HuggingFace 下载的 Q5_K_M 版本），可以直接用 Modelfile 创建 Ollama 模型：

```bash
# 创建 Modelfile
cat > /tmp/qwen3-8b-q5kmodelfile << 'EOF'
FROM /path/to/your/qwen3-8b-q5_k_m.gguf
EOF

# 导入 Ollama
ollama create qwen3:8b-q5km -f /tmp/qwen3-8b-q5kmodelfile

# 使用
ollama run qwen3:8b-q5km
```

#### 方案 C：从 Ollama 已有的 blob 重新量化（高级）

Ollama 的 blob 已经是 Q4_K_M，如果想在不重新下载的情况下重新量化：

```bash
# 找到当前 qwen3:8b 的 blob 路径（从日志中可见）

# 用 ollama 自带的 llama-quantize（如果存在）
# 通常位于：C:\Users\Administrator\AppData\Local\Programs\Ollama\lib\ollama\
# 或 llama.cpp 的构建目录中

# 如果没有独立的 quantize 工具，可以：
# 1. 用 ollama pull qwen3:8b-q5km（如果 Ollama 仓库有该量化版本）
# 2. 或从 HuggingFace 下载预量化的 GGUF：
#    https://huggingface.co/Qwen/Qwen3-8B-GGUF
```

### 1.5 thinking 模式与量化的关系

**Qwen3 的 thinking 模式在量化后仍然可用，但有以下注意事项**：

1. **thinking 模式本质是推理策略，不是模型权重的一部分**。Qwen3 的 thinking 通过 chat template 中的特殊标记（` thinking` / `</think>`）和推理时的参数控制，与量化无关。
2. **量化对 thinking 质量的影响**：
   - Q4_K_M 下：thinking 的逻辑推理能力基本无损（4~7% 的精度损失主要影响罕见 token 和细微语义，对逻辑链影响小）
   - Q3_K_M 下：thinking 的深度推理可能出现轻微跳步，不推荐
   - Q5_K_M 下：thinking 质量与 Q4_K_M 几乎无差异
3. **thinking 模式在 Ollama 中的开启方式**：
   - Modelfile 中设置 `PARAMETER num_ctx 32768`（thinking 需要更大的上下文）
   - 通过 `keep_alive` 延长模型驻留时间（thinking 生成较长）
   - 在请求中使用 `think: true` 参数（Ollama API 支持）
4. **量化后 thinking 的性能影响**：thinking 模式通常需要生成 1000~5000 token 的中间推理，量化带来的 10~15% 速度提升在此场景下收益明显。

**结论**：Q4_K_M 量化不阻碍 thinking 模式，可以放心使用。如果追求极致 thinking 质量，用 Q5_K_M；如果追求体积和速度，Q4_K_M 足够。

## 2. Ollama 运行参数调优

### 2.1 当前配置问题

从日志中可以看到当前运行参数：
- `n_parallel=1`（单请求串行，浪费资源）
- `keep_alive=5m`（5 分钟后卸载模型，再次请求需重新加载）
- `num_ctx=4096`（默认值，Qwen3 支持 40960，但 CPU 下 4096 已是合理起点）
- `temperature=0.6`（默认值，适合通用对话，编程可更低）
- 未开启 thinking
- 未使用 `num_gpu`（核显不可用，纯 CPU）

### 2.2 推荐参数配置（针对 i5-12400 / 32GB / 纯 CPU）

| 参数 | 推荐值 | 原因 |
|------|-------|------|
| **num_ctx** | 8192（起步）/ 16384（内存允许） | Qwen3 原生支持 40960 上下文。8192 在 CPU 下 prompt eval 约 120~140s，16384 约 240~280s。根据实际需求选择。编程场景建议 8192。 |
| **num_gpu** | 0（纯 CPU） | 核显 UHD 730 Vulkan compute=0.0，不可用。如果未来升级独显，设为 1。 |
| **num_thread** | 8~12（自动或手动） | i5-12400 是 6 核 12 线程，Ollama 默认使用 6 线程。建议设为 8~10（超线程对矩阵运算有帮助）。设为 0 让 Ollama 自动检测。 |
| **temperature** | 0.2~0.3（编程）/ 0.5~0.7（通用） | 编程任务需要确定性输出，低温度更好。 |
| **top_p** | 0.9（编程）/ 0.95（通用） | 保持多样性的同时避免极端选择。 |
| **repeat_penalty** | 1.1~1.2 | 减少重复输出，对长文本生成有效。 |
| **num_parallel** | 2~4 | 允许同时处理多个请求（需要足够内存）。每个请求需要独立的 KV cache（约 576 MiB @ ctx=4096，8192 约 1.1 GiB）。32GB 内存下最多 4~6 个并发。 |
| **keep_alive** | 30m~1h 或 24h | 避免频繁卸载/加载模型（加载约 7~8s）。开发场景建议 1h 或更长。 |
| **flash_attention** | auto（默认） | Qwen3 支持 fused Gated Delta Net 等优化，保持 auto。 |
| **thinking** | 开启 | 通过 `think: true` 或 Modelfile 参数开启。 |

### 2.3 完整 Modelfile（可直接使用）

保存为 `scripts/02-Modelfile-qwen3-8b`：

```dockerfile
# Qwen3 8B 优化配置（CPU 推理 · 编程助手场景）
# 用法：ollama create qwen3:8b-opt -f 02-Modelfile-qwen3-8b
#      ollama run qwen3:8b-opt

FROM qwen3:8b

# ─── 上下文长度 ───
# Qwen3 原生支持 40960，CPU 下 8192 是务实选择
# 如果内存紧张（<16GB 可用），设为 4096
PARAMETER num_ctx 8192

# ─── 线程数 ───
# i5-12400 是 6C/12T，设 0 让 Ollama 自动检测（通常取 6~8）
# 也可手动设为 10 以利用超线程
PARAMETER num_thread 0

# ─── GPU 配置 ───
# 核显 UHD 730 不可用，纯 CPU 推理
# PARAMETER
 num_gpu 0   # 纯 CPU；未来加装独显后改为 1

# ─── 采样参数 ───
# 编程/结构化输出用低温度更稳；闲聊可调回 0.6
PARAMETER temperature 0.3
PARAMETER top_p 0.9
PARAMETER repeat_penalty 1.1

# ─── 并发 ───
# 32GB 内存下 2 路并发安全（每路 KV cache 约 1.1 GiB @ 8192）
# 服务级并发用环境变量 OLLAMA_NUM_PARALLEL=2

SYSTEM """你是一个专业的中文编程助手。回答要求：
1. 简洁准确，先给结论再给解释。
2. 代码必须完整可运行，用 Markdown 代码块并标注语言。
3. 不确定的 API 或版本号要明确说明"不确定"，禁止编造。
4. 涉及企业数据时遵守最小化原则，不主动索取敏感信息。"""
```

创建优化模型：

```bash
ollama create qwen3:8b-opt -f scripts/02-Modelfile-qwen3-8b
ollama run qwen3:8b-opt "写一个快速排序"
```

### 2.4 服务级环境变量（配合 Modelfile）

| 环境变量 | 推荐值 | 作用 |
|---------|-------|------|
| `OLLAMA_KEEP_ALIVE` | `1h` | 模型常驻，省掉每次 7~8s 加载 |
| `OLLAMA_NUM_PARALLEL` | `2` | 2 路并发（内存允许可 4） |
| `OLLAMA_MAX_LOADED_MODELS` | `1` | 32GB 内存只驻留 1 个大模型 |
| `OLLAMA_FLASH_ATTENTION` | `1` | 启用 Flash Attention（降低 KV 显存/提速） |
| `OLLAMA_KV_CACHE_TYPE` | `q8_0` | KV cache 量化，576MiB→约 288MiB，精度几乎无损 |
| `OLLAMA_IGPU_ENABLE` | `1` | 尝试启用核显（UHD 730 大概率仍不可用，可试一次） |

## 3. 领域微调（LoRA/QLoRA）

### 3.1 适用性判断

本机纯 CPU **无法训练**（8B 模型 QLoRA 4bit 也需约 10GB 显存 / 48GB 内存）。微调脚本供有 GPU 的机器使用（如 RTX 4090 / 云端 A10）。若只是想让模型更懂"中文编程 + 企业问答"，**优先用 RAG（检索增强）+ 提示词**，性价比远高于微调；只有当风格、格式、领域术语要求极高时才上 LoRA。

### 3.2 数据准备（JSONL）

每条样本一个 JSON，50~500 条起步即可见效：

```jsonl
{"instruction": "把下面的订单金额计算改成按分存储", "input": "total = price * count", "output": "totalCents = Math.round(price * 100) * count\n// 金额一律用整数分存储，避免浮点误差"}
{"instruction": "解释什么是利润分红中的'超额累进分红'", "input": "", "output": "超额累进分红指……"}
```

### 3.3 QLoRA 训练脚本

见 `scripts/03-finetune-lora.py`（transformers + peft + bitsandbytes，4bit 量化基座 + LoRA rank 16）。

### 3.4 合并导出并回到 Ollama

```bash
# 训练完成后合并 LoRA 权重并导出 GGUF，再导入 Ollama
python scripts/03-finetune-lora.py --merge-only
ollama create qwen3:8b-ft -f Modelfile.ft   # FROM 指向合并后的 GGUF
```

## 4. 推理服务优化（Ollama vs llama.cpp vs vLLM）

### 4.1 选型对比（针对本机纯 CPU 场景）

| 维度 | Ollama | llama.cpp server | vLLM |
|------|--------|------------------|------|
| CPU 推理 | ✅ 开箱即用 | ✅ 同底层，调优空间更大 | ❌ 主要面向 GPU |
| 连续批处理 | 有限（n_parallel） | ❌ 无（单请求为主） | ✅ 最强（GPU） |
| KV cache 量化 | ✅ `OLLAMA_KV_CACHE_TYPE` | ✅ `--cache-type-k/v q8_0` | ✅ |
| 吞吐上限（CPU） | ~5 tok/s | ~5-7 tok/s（`-t` 调优后） | 不适用 |
| 运维成本 | 最低 | 中 | 高（需 GPU） |

**结论**：本机继续用 Ollama（省心），极限压榨换 llama.cpp server；vLLM 只在将来上 GPU 后考虑。

### 4.2 llama.cpp server 调优命令

见 `scripts/04-serve-llamacpp.sh`，关键点：

```bash
./llama-server -m qwen3-8b-q4_k_m.gguf \
  -t 8 \                    # 线程数=物理核+2
  -c 8192 \                 # 上下文
  --mlock \                 # 锁内存避免换页抖动
  --cache-type-k q8_0 \     # KV cache 量化
  --cache-type-v q8_0 \
  --parallel 2 \            # 2 路并发槽位
  --host 127.0.0.1 --port 8080
```

### 4.3 通用优化清单

- **prompt eval 是首 token 延迟大头**（实测 2050 tokens 要 62s）：把固定内容（system prompt、few-shot）放在**前缀最前面并保持不变**，Ollama 的 prompt cache（已启用，上限 8GiB）会复用，第二轮起接近 0 计算。
- **`--mlock`**：32GB 内存充足，锁住模型避免 swap 抖动。
- **避免上下文震荡**：多轮对话裁剪历史时保留公共前缀，否则缓存全失效。

## 5. 提示词与上下文优化

### 5.1 System Prompt 模板（编程助手场景）

```
你是飞虹 Code 的本地编程助手（qwen3:8b）。
规则：
1. 只输出与任务相关的代码与说明，不要寒暄。
2. 修改代码时给出完整函数，不要用省略号。
3. 不确定的 API 行为明确标注"需验证"，禁止编造。
4. 输出语言：简体中文；代码与命令：英文。
```

### 5.2 Few-shot 策略

- 放 **2~3 个**高质量示例即可（CPU 下示例越多 prompt eval 越慢）。
- 示例与真实任务**格式一致**（都是 JSONL/都是函数签名补全），比数量重要。
- 把示例固化进 Modelfile 的 SYSTEM 里，享受 prompt cache。

### 5.3 上下文裁剪

| 场景 | 策略 |
|------|------|
| 多轮对话 | 只保留最近 3~5 轮 + 首轮任务描述，中间轮次丢弃 |
| 长文件注入 | 只贴相关函数/类（用 grep 定位行号再切片），不整文件塞入 |
| 工具结果 | 截断到关键 200 行内，大日志先 `tail`/`grep` |
| thinking 模式 | 简单任务关闭（`think: false`），省 1000+ token 生成时间 |

## 6. 优先级排序（结论）

| 优先级 | 动作 | 预期收益 | 成本 |
|--------|------|---------|------|
| **P0** | `OLLAMA_KEEP_ALIVE=1h` + `OLLAMA_NUM_PARALLEL=2` + `OLLAMA_KV_CACHE_TYPE=q8_0` | 消除 7~8s 重载、支持并发、内存省 288MiB | 零，改环境变量 |
| **P0** | 用 `scripts/02-Modelfile-qwen3-8b` 创建 `qwen3:8b-opt`（ctx 8192 + 低温度 + 编程 SYSTEM） | 输出更稳、上下文翻倍 | 零，一条命令 |
| **P1** | System prompt 固化前缀 + few-shot 2~3 例 + 历史裁剪 | 首 token 延迟大幅下降（prompt cache 命中） | 零 |
| **P1** | thinking 按需开关（复杂推理开、简单任务关） | 简单任务提速 3~5 倍 | 零 |
| **P2** | 换 Q5_K_M（`ollama pull` 或 HF 下载 GGUF 导入） | 质量提升 2~4%，速度略降 | 需下载 ~5.4GB |
| **P2** | 极限调优换 llama.cpp server（`--mlock` + 线程调优） | 吞吐 +20~40% | 中，需编译 |
| **P3** | QLoRA 领域微调（需 GPU 机器）+ RAG 知识库 | 领域契合度质变 | 高（硬件/数据） |
| **P3** | 上独显（哪怕 RTX 3060 12G）+ vLLM | 吞吐质变（10 倍级） | 硬件投入 |

> **一句话结论**：当前机器瓶颈在 CPU 吞吐与首 token 延迟，不在模型本身——P0/P1 的零成本调参（常驻 + 并发 + KV 量化 + prompt cache 前缀固化）就能把日常体验提升一大截；量化维持 Q4_K_M 即可；微调前先试 RAG。
