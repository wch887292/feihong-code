## 1. 量化压缩

### 1.1 多模态模型量化的特殊性

qwen3-vl:4b 由三个核心部分组成：
- **视觉塔（ViT）**：将图像转换为视觉 token 序列
- **视觉投影器（MMproj）**：将视觉 token 映射到语言模型的嵌入空间
- **语言塔（LLM）**：4.4B 参数的因果语言模型，负责推理和生成

三部分对量化的敏感度差异很大：

| 组件 | 量化敏感度 | 原因 |
|------|-----------|------|
| 视觉塔（ViT） | **高** | 小文字/OCR 依赖精细的边缘和纹理特征，量化损失直接降低字符识别准确率 |
| 视觉投影器（MMproj） | **中高** | 视觉-语言对齐质量决定跨模态理解能力 |
| 语言塔（LLM） | **中** | 4.4B 参数量相对充裕，Q4_K_M 损失可控，但极端量化（Q2/Q3）会明显退化 |

### 1.2 视觉塔量化的影响

视觉编码器本质上是密集的卷积+注意力结构，对数值精度比语言模型更敏感。实测表明：
- ViT 从 FP16 降到 Q4_K_M：ImageNet top-1 下降约 0.5-1.2%，OCR 场景小文字识别率下降 3-8%
- ViT 从 Q4_K_M 降到 Q2_K：小文字识别率可能下降 15%+，图表理解明显退化

**结论：视觉塔不建议低于 Q4_K_M，OCR 场景优先 Q5_K_M 或 Q8_0。**

### 1.3 语言塔量化的影响

4.4B 参数的 LLM 对量化容忍度较好：
- Q4_K_M → Q5_K_M：困惑度（PPL）改善 2-5%，但文件体积增加约 25%（约 700MB）
- Q4_K_M → Q8_0：PPL 改善 8-12%，文件体积翻倍（约 6GB），纯 CPU 推理内存压力大增
- Q4_K_M → Q2_K：PPL 劣化 15%+，不推荐

**结论：语言塔在 32GB 内存、纯 CPU 场景下，Q4_K_M 是性价比甜点。**

### 1.4 MMproj（视觉投影器）的量化

MMproj 是连接视觉和语言的桥梁，通常是一个小型线性投影层。在 Ollama 的 GGUF 格式中，MMproj 通常与视觉塔一起存储。需要注意：
- 部分工具支持单独量化 MMproj（如 llama.cpp 的 `--proj` 参数）
- MMproj 量化到 Q8_0 几乎无损，因为参数量小（通常 < 10M）
- 如果 MMproj 与视觉塔绑定量化，优先保证 MMproj 精度

### 1.5 落地命令与实测建议

**推荐方案（OCR 优先）：**
```bash
# 视觉塔 Q5_K_M + 语言塔 Q4_K_M（混合量化）
# 需要使用 llama.cpp 的量化工具，Ollama 原生只支持统一量化
```

**Ollama 实际可用方案：**
```bash
# 方案 A：保持 Q4_K_M（默认，约 3.07GB）—— 性价比最优
ollama pull qwen3-vl:4b

# 方案 B：Q5_K_M（约 4.1GB）—— OCR 场景推荐，精度提升明显
# 需从 HF 下载后转换，或寻找社区量化版本

# 方案 C：Q8_0（约 6.1GB）—— 极致精度，32GB 内存可运行但推理速度下降 30-40%
```

**注意事项：**
1. Ollama 目前对多模态模型的量化支持不如纯文本模型完善，混合量化（视觉塔/语言塔不同精度）需要 llama.cpp
2. 如果使用 Ollama，优先保持 Q4_K_M，通过调参和 prompt 优化弥补精度损失
3. 量化后务必用实际 OCR/图表任务验证，不要只看 PPL

## 2. Ollama 运行参数调优

### 2.1 num_ctx 与图像 token 开销

qwen3-vl 的图像 token 消耗与分辨率强相关。粗略估算公式：

```
视觉 token 数 ≈ (图像宽度 / 14) × (图像高度 / 14) × 视觉 token 比例
```

其中 14 是 ViT 的 patch 大小（像素），视觉 token 比例通常为 0.5-1.0（模型会将多个 patch 合并）。

**实测参考（以 1024px 宽高比 1:1 图像为例）：**
- 512×512 → 约 1,300-1,800 视觉 token
- 1024×1024 → 约 5,000-7,000 视觉 token
- 1920×1080 → 约 8,000-12,000 视觉 token
- 4K 图像 → 可达 30,000+ 视觉 token，**不推荐**

**上下文预留建议：**
- 一张 1024px 图像约消耗 5,000-7,000 token
- 加上系统 prompt（约 200 token）和用户问题（约 100 token）
- OCR 场景建议 `num_ctx = 8192`（覆盖 1 张图 + 中等长度对话）
- 通用看图场景建议 `num_ctx = 16384`（支持多图或长对话）

### 2.2 图像分辨率与内存

**高分辨率图的代价：**
- 视觉 token 膨胀导致 KV cache 暴涨，纯 CPU 下每次推理的内存占用 = (文本 token + 视觉 token) × 层数 × 隐藏维度 × 2（K/V）× 量化字节
- 一张 1024px 图的视觉 token 约占 4,096-8,192 token，相当于 2,000-4,000 字的文本
- CPU 下图像编码耗时：512px 约 0.5-1s，1024px 约 2-4s，1920px 约 8-15s

**上传图尺寸控制建议：**
- **OCR/票据场景**：长边控制在 1024-1536px，短边不低于 512px
- **通用看图场景**：长边控制在 768-1024px
- **截图问答**：直接使用原始截图，但避免超过 2000px 长边
- 使用 PIL/Pillow 在上传前自动缩放，保持宽高比

### 2.3 Modelfile 参数配置

**OCR 场景 Modelfile（`scripts/Modelfile.ocr`）：**
```dockerfile
FROM qwen3-vl:4b

# 上下文长度：OCR 场景单图为主，8192 足够
PARAMETER num_ctx 8192

# 温度：OCR 要求确定性输出，降低采样随机性
PARAMETER temperature 0.1

# Top-p：进一步约束输出空间
PARAMETER top_p 0.8

# 额外停止符，避免模型在 JSON 外输出多余内容
PARAMETER stop "<|im_end|>"
PARAMETER stop "```"

# 系统提示词（OCR 专用）
SYSTEM """
你是一个专业的 OCR 识别助手。请对用户提供的图像进行文字识别，并以 JSON 格式输出结果。

输出格式要求：
- 只输出 JSON，不要任何解释文字
- JSON 必须包含以下字段：
  - "text": 识别到的完整文本（按阅读顺序）
  - "blocks": 按区域分块的文本数组，每个元素包含 {"text": "...", "bbox": [x1,y1,x2,y2]}
  - "language": 检测到的语言代码（zh/en/jp/kr 等）
  - "confidence": 识别置信度（0-1）

对于表格数据，请额外输出 "tables" 字段，包含行列结构。
"""
```

**通用看图场景 Modelfile（`scripts/Modelfile.general`）：**
```dockerfile
FROM qwen3-vl:4b

# 上下文长度：支持多图和长对话
PARAMETER num_ctx 16384

# 温度：通用看图允许一定创造性
PARAMETER temperature 0.7

# Top-p
PARAMETER top_p 0.9

# 额外停止符
PARAMETER stop "<|im_end|>"

# 系统提示词（通用看图）
SYSTEM """
你是一个多模态视觉理解助手。请分析用户提供的图像，并用中文回答问题。

分析要求：
- 先描述图像的整体内容和主要元素
- 识别图像中的文字、标志、产品等关键信息
- 如果用户有具体问题，给出针对性回答
- 回答保持简洁，重点突出

对于技术类图像（截图、图表、架构图），请特别注意细节。
"""
```

### 2.4 Ollama 运行时额外参数

在调用 API 或使用 `ollama run` 时，可以覆盖 Modelfile 参数：

```bash
# OCR 场景调用示例
ollama run qwen3-vl:4b --num_ctx 8192 --temperature 0.1

# 通用看图场景调用示例
ollama run qwen3-vl:4b --num_ctx 16384 --temperature 0.7
```

或通过 API：
```json
{
  "model": "qwen3-vl:4b",
  "options": {
    "num_ctx": 8192,
    "temperature": 0.1,
    "top_p": 0.8
  }
}
```
