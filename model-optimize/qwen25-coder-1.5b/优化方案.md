# qwen2.5-coder:1.5b 优化提升方案

> 目标模型：`qwen2.5-coder:1.5b`（Q4_K_M 量化，约 0.92GB，支持 FIM 补全）
> 运行环境：Intel i5-12400（6C12T）/ 32GB 内存 / 纯 CPU 推理
> 分析日期：2026-10-01

---

## 0. 模型画像与优化定位

qwen2.5-coder:1.5b 是通义千问 2.5 代码系列的小参数版本，核心能力在**单文件/单函数级代码补全、语法纠错、小片段翻译**。1.5B 参数在 CPU 上推理极快（预期 50–120 token/s），但复杂逻辑、长上下文、架构设计是它的天花板。

本方案的优化主线只有一条：**把 1.5B 的"快"做到极致，同时用分层路由把"重"甩给 8B 模型**。所有 5 个方向都服务于这个定位。

**一句话结论：1.5B 模型体积小、显存/内存压力低，最大的优化空间不在精度而在"用法"——量化升档到 Q8_0 几乎零成本、FIM 补全模式是核心价值、LoRA 微调是拉开与通用模型差距的关键手段。**

## 1. 量化压缩

### 1.1 现状与判断

当前模型是 Q4_K_M 量化，约 0.92GB。对于 1.5B 参数的模型，Q8_0 体积约 1.5GB，精度几乎无损（相对 Q4_K_M 的 PPL 上升通常 < 1%）。**结论：值得换，性价比极高。**

- Q4_K_M → Q8_0：内存占用从 0.92GB 升到约 1.5GB（本机 32GB 完全无压力），推理速度几乎不变（同为 4-bit/8-bit 量化，CPU 推理瓶颈在矩阵乘法而非位宽），但代码补全的准确率提升明显，尤其在**字符串拼接、缩进、括号配对**等细粒度场景。
- 如果要更激进：Q4_K_M 已经是 K-quant 的均衡档，不建议再往下压到 Q3_K_M（1.5B 下精度损失会比较明显）。

### 1.2 落地命令

**方式一：Ollama Modelfile 直接引用 Q8_0 GGUF（推荐，最简单）**

先确保本地已有 Q8_0 版本的 GGUF 文件（可从 HuggingFace qwen2.5-coder-1.5b-GGUF 仓库下载），然后：

```
FROM ./qwen2.5-coder-1.5b-q8_0.gguf
PARAMETER temperature 0.1
PARAMETER num_ctx 4096
```

构建：`ollama create qwen25-coder-1.5b-q8 -f Modelfile`

**方式二：llama.cpp 原生命令（如果从原始权重转换）**

```bash
# 安装/编译 llama.cpp
git clone https://github.com/ggerganov/llama.cpp
cd llama.cpp && make -j$(nproc)

# 转换 HF 权重 → GGUF（fp16）
python convert_hf_to_gguf.py ./qwen2.5-coder-1.5b --outtype f16

# 量化到 Q8_0
./llama-quantize ./qwen2.5-coder-1.5b-f16.gguf ./qwen2.5-coder-1.5b-q8_0.gguf Q8_0
```

**方式三：Ollama 拉取已量化版本（无需手动转换）**

```bash
# 从 Ollama Registry 拉取（如果社区提供了 Q8_0 tag）
ollama pull qwen2.5-coder:1.5b-q8_0
# 或者用 Modelfile FROM 已有的 Q4_K_M 模型重新导出（不推荐，精度不会自动提升）
```

### 1.3 预期收益与性价比

| 档位 | 体积 | 推理速度（token/s） | 代码补全准确率变化 | 性价比 |
|------|------|---------------------|-------------------|--------|
| Q4_K_M（当前） | 0.92GB | 50–120 | 基准 | — |
| Q8_0 | ~1.5GB | 45–115 | +3–8%（绝对值） | ★★★★★ |
| Q4_K_M → FP16 | ~2.8GB | 30–80 | +1–2% | ★★☆☆☆ |

**性价比判断：Q8_0 是最优解。** 多出的 0.6GB 内存在 32GB 容器里可以忽略，但精度提升对代码场景是实打实的。不建议上 FP16（体积翻 3 倍，收益边际递减）。

## 2. Ollama 运行参数调优

### 2.1 核心参数选型逻辑

| 参数 | 代码补全场景 | 对话问答场景 | 说明 |
|------|-------------|-------------|------|
| `num_ctx` | 2048 | 4096 | 补全只需要当前文件局部上下文；问答需要更长对话窗口 |
| `num_predict` | 256 | 2048 | 补全必须限制输出长度防跑飞，问答可以放开 |
| `temperature` | 0.1 | 0.5 | 补全要确定性高，问答允许一定随机性 |
| `top_k` | 5 | 50 | 补全从 top-5 候选里选，问答放宽 |
| `top_p` | 0.1 | 0.9 | 配合 top_k 使用 |
| `stop` | 必须含 FIM 结束标记和代码块结束标记，防止补全"跑飞"（详见第 3 章 FIM 说明） | 常规 `["\n"]` | 补全场景 stop 漏配是最常见的"跑飞"原因，必须显式配置 |

### 2.2 线程参数（num_thread）

本机 i5-12400 是 6 核 12 线程，物理 6 核。对于 1.5B 模型的 CPU 推理：

- `num_thread` 建议设为 **6**（物理核数），不要设为 12。纯 CPU 推理中，逻辑线程在单核内切换会引入同步开销，超过物理核数后吞吐反而下降。
- Ollama 默认 `num_thread = 4`（Ollama 自身保守策略），对 1.5B 这种小模型来说略保守，显式设为 6 能多榨出 15–25% 吞吐。
- 如果同时跑多个模型（1.5b + 8b 共存），线程总数要拆分配额，避免线程争抢。

**经验公式：** `num_thread = 物理核数`，如果同时跑 N 个模型，`num_thread_i ≈ 物理核数 / N`。
