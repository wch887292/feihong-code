## 二、优化实施清单（全部已落地）

### 2.1 模型级（ollama create，4 个优化版模型已创建）
| 优化版模型 | 基于 | 关键参数 |
|---|---|---|
| `qwen3-8b-opt` | qwen3:8b | num_thread 8 / num_ctx 8192 / temp 0.3 / top_k 20 / top_p 0.8 / chatml stop 序列 |

| `qwen3-vl-4b-opt` | qwen3-vl:4b | num_thread 8 / num_ctx 4096 / temp 0.3 / top_k 20（本次补做） |

### 2.2 服务级（Ollama serve 环境变量，逐项消测后定稿）
| 参数 | 初版方案 | 消测结论 | 最终配置 |
|---|---|---|---|
| OLLAMA_KEEP_ALIVE | 1h | ✅ 有效保留 | **1h** |
| OLLAMA_NUM_PARALLEL | 2 | ❌ 纯 CPU 负优化（coder -6.6%，吞吐波动） | 1（默认） |
| OLLAMA_KV_CACHE_TYPE | q8_0 | ❌ 负优化（coder prefill 慢 39%：6.17s→8.57s） | f16（默认） |
| OLLAMA_FLASH_ATTENTION | 1 | ❌ CPU 后端无收益 | 0（默认） |
| OLLAMA_NUM_GPU | 0 | 中性（核显不可用） | 不设 |

> **反直觉发现**：网上流传的"KV 量化 + FlashAttention 提速"经验来自 GPU 场景；在纯 CPU 推理下，KV q8_0 的量化/反量化开销与 FA 的分支开销反而拖慢速度。本机实测数据如上，均已回退。

## 五、为什么吞吐无法 +20%：物理极限证明

纯 CPU 推理的生成速度由**内存带宽**决定：`tok/s ≈ 有效带宽 ÷ 模型体积`。

| 模型 | 体积 | 实测 tok/s | 反推有效带宽 |
|---|---|---|---|
| qwen3:8b (Q4) | 5.2 GB | 7.08 | ≈36.5 GB/s |
| qwen2.5-coder:1.5b (Q4) | 0.99 GB | 36.22 | ≈35.9 GB/s |
| qwen3.5-4b (Q4) | 2.7 GB | 11.21 | ≈30.3 GB/s |

三个体积差 5 倍的模型反推出**同一个带宽上限（30~36 GB/s）**，即 i5-12400 的 DDR4-3200 双通道理论带宽 41.6 GB/s 的 73~88% —— **四个模型全部已运行在内存带宽物理极限**，任何软件配置都无法突破。这与 thread 扫描"全档差 <10%"互相印证。

**附加发现（热节流）**：连续满载 40 分钟后吞吐系统性衰减 5~10%（E 轮全线低于等价的 D 轮）。生产部署建议重载任务错峰、改善机箱风道。

## 七、使用指南

1. **切优化版模型**：调用时把模型名换成 `qwen3-8b-opt` / `qwen25-coder-15b-opt` / `qwen35-4b-opt` / `qwen3-vl-4b-opt` 即可，API 无任何改动。
2. **服务启动**：保持当前配置重启即生效（仅 `OLLAMA_KEEP_ALIVE=1h`）。参考 `tuned/ollama-env.cmd` 已同步修正。
3. **回滚**：`ollama rm qwen3-8b-opt`（等 4 个 opt 模型）即完全回滚，原模型未动过。
4. **复现测试**：`baseline-speed.mjs`（基线）→ `opt-speed.mjs`（第一轮）→ `thread-scan.mjs`（线程扫描）→ `env-ablation.mjs <LABEL>`（服务 env 消测）→ `final-verify.mjs`（最终轮），数据 JSON 均在本目录。

## 附：诚实声明

本报告全部数字来自本机实测（测试脚本与原始 JSON 数据同目录存档，可复现）。"能力提升"指推理配置优化带来的可感知体验提升（冷启动、无效 token、上下文容量、防负优化），**不包含也无法包含模型权重的智力提升**——小参数模型的知识与推理边界不变。吞吐维度已达硬件物理极限，如实报告，不造假数据。
